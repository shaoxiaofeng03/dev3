## 卡片清单（快速浏览 / 打印）

### 1. 为什么 AI 服务接口要支持流式（SSE）？

**答**：首 token 延迟远小于完整生成时间（可能几秒到几十秒）。流式让用户立刻看到反馈，感知延迟大幅下降。代价：错误处理更复杂（中途失败）、需要处理断流与重连、代理不能缓冲。

<small>标签：服务 · ID：w4-c1</small>

### 2. SSE 和 WebSocket 怎么选？

**答**：SSE：单向服务器推送、基于 HTTP、自动重连、实现简单，适合「提问 → 流式回答」。WebSocket：双向、低延迟、需心跳与连接管理，适合实时协作/语音。大多数 LLM 对话用 SSE 就够。

<small>标签：服务 · ID：w4-c2</small>

### 3. AI 接口设计要特别注意哪几点？

**答**：① 幂等与去重（防止重复计费）；② 超时与取消（用户关闭页面要停止生成）；③ 流式错误如何回传；④ 限流与配额（按用户/租户）；⑤ 版本化（prompt 与模型都要能回滚）；⑥ 输入长度与内容安全校验。

<small>标签：服务 · ID：w4-c3</small>

### 4. 增量索引怎么判断「文档变了」？

**答**：对文档内容算 hash（或 mtime+size 快速判断），与库中记录比对：新增则插入、hash 变则删旧插新、源文件消失则软删除。关键：块 id 要可推导（docId+chunkIndex），保证重复执行幂等。

<small>标签：管道 · ID：w4-c4</small>

### 5. 为什么要做块级去重？

**答**：模板化文档（合同、制度）有大量重复段落，会挤占 top-k、放大错误。去重方式：内容 hash 精确去重、MinHash/SimHash 近似去重。另外同一文档的相邻块重叠也会造成重复召回，需要按 doc 聚合。

<small>标签：管道 · ID：w4-c5</small>

### 6. RAG 评测的核心指标有哪些？

**答**：检索侧：Recall@k、命中率、MRR；生成侧：忠实度（是否只依据证据）、答案正确率、引用正确率；工程侧：P95 延迟、单次成本、拒答准确率。指标要配「评测集 + 可复现命令」，否则只是感觉。

<small>标签：评测 · ID：w4-c6</small>

### 7. 没有人工标注，怎么快速搭评测集？

**答**：① 从真实日志/文档里抽问题；② 用强模型基于片段生成「问题-答案-证据」三元组，再人工抽检修正；③ 保留 20% 人工全标作为金标准；④ 加入「无答案」样本测拒答。冷启动阶段 50–100 条就够用。

<small>标签：评测 · ID：w4-c7</small>

### 8. 为什么每次只能改一个变量？

**答**：RAG 是多环节耦合系统，同时改切分和 rerank，分数涨了也不知道是谁的功劳、下次该往哪调。单变量 + 固定评测集 = 可归因。工程上把配置外置成参数，评测脚本一键跑多组配置。

<small>标签：评测 · ID：w4-c8</small>

### 9. 一次 RAG 请求的 trace 应该包含什么？

**答**：request_id、用户与租户、原始 query 与改写后 query、召回的全部候选（id/分数/来源）、rerank 后顺序、最终 prompt（或 hash + 版本）、模型与参数、首 token 与总耗时、token 与费用、输出、用户反馈。

<small>标签：可观测 · ID：w4-c9</small>

### 10. 为什么 prompt 也要版本化？

**答**：prompt 是「代码」，改动会直接影响效果与成本。版本化后可以：A/B 对比、快速回滚、把线上问题归因到具体版本、在 trace 里定位当时用的哪版。建议 prompt 存文件/配置中心，带版本号与变更记录。

<small>标签：可观测 · ID：w4-c10</small>
