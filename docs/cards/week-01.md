## 卡片清单（快速浏览 / 打印）

### 1. LLM 应用的四种形态是什么？各自解决什么问题？

**答**：① Prompt 工程：不改模型，靠输入设计提升效果，成本最低；② RAG：把外部知识检索进上下文，解决「不知道」和「知识过期」；③ Agent：让模型决定调用工具、分步执行，解决「不会做」；④ 微调：改变模型行为/风格/领域能力，成本最高。选型顺序通常是 Prompt → RAG → Agent → 微调。

<small>标签：全景 · ID：w1-c1</small>

### 2. 什么是 token？为什么它决定了成本和延迟？

**答**：token 是模型处理文本的最小单位（约等于 0.5–1 个汉字或 0.75 个英文单词）。API 按输入+输出 token 计费，上下文越长、输出越长越贵；token 越多，推理耗时越长（尤其是输出 token）。所以「塞满上下文」既贵又慢。

<small>标签：基础 · ID：w1-c2</small>

### 3. 上下文窗口和最大输出长度是一回事吗？

**答**：不是。上下文窗口 = 输入 + 输出共享的总预算；最大输出长度是单次生成的上限。超窗口必须做截断、摘要或检索，而不是硬塞。

<small>标签：基础 · ID：w1-c3</small>

### 4. temperature 和 top_p 分别控制什么？怎么选？

**答**：temperature 缩放概率分布：越低越确定、越高越发散；top_p 是核采样，只在累计概率前 p 的候选里采样。实践：抽取/分类/代码用 0–0.3；创意写作用 0.7–1.0；一般不要同时大改两个。

<small>标签：参数 · ID：w1-c4</small>

### 5. 流式输出（SSE）的原理和实现要点？

**答**：服务端用 text/event-stream 持续推送增量 chunk，客户端边收边渲染。要点：正确处理半包/粘包、区分首 token 延迟和总时长、流中断要能续或提示、代理层需关闭缓冲。

<small>标签：流式 · ID：w1-c5</small>

### 6. 让模型输出结构化数据，有哪几种做法？

**答**：① JSON mode / 原生结构化输出（由服务端约束）；② 工具调用（function schema）间接产出；③ 提示词约束 + 解析 + 失败重试（最通用）。生产上要「schema 校验 + 重试 + 兜底」，不能假设模型一次就对。

<small>标签：结构化输出 · ID：w1-c6</small>

### 7. 幻觉的三个主要成因和对应缓解手段？

**答**：① 知识缺失：模型没有该知识 → 用 RAG 提供证据并要求引用；② 训练数据偏差/过时 → 检索 + 时效性说明；③ 任务要求超出能力（多步推理、精确计算）→ 拆解任务、给工具（计算器/代码执行）。另加：允许模型说「不知道」。

<small>标签：幻觉 · ID：w1-c7</small>

### 8. 为什么重试要指数退避？为什么还要加抖动？

**答**：限流/瞬时故障时立即重试会放大拥塞；指数退避让等待时间递增。加随机抖动（jitter）避免大量客户端同一时刻重试造成「惊群」。配合最大重试次数、幂等键和熔断。

<small>标签：工程 · ID：w1-c8</small>

### 9. AI 应用为什么必须做可观测性？要记哪些字段？

**答**：模型输出不确定、链路长、成本浮动，出问题无法靠「看代码」定位。至少记：请求 id、模型与参数、prompt 版本、检索片段及分数、token 与费用、各阶段耗时、重试次数、最终输出与是否被用户采纳。

<small>标签：工程 · ID：w1-c9</small>

### 10. RAG、长上下文、微调，什么时候用哪个？

**答**：知识频繁更新、要求引用溯源、需要权限隔离 → RAG；一次性长文档理解、上下文能装下 → 长上下文（现在的模型上下文已到 1M，但塞满仍然贵且慢，缓存未命中的输入价与命中价差一个数量级）；需要稳定输出风格/领域术语/降低小模型成本 → 微调。三者常组合：RAG 供知识 + 微调定行为 + 长上下文做深度阅读。

<small>标签：选型 · ID：w1-c10</small>

### 11. 为什么大家都提供「OpenAI 兼容接口」？对你有什么好处？

**答**：统一了 messages / tool_calls / usage 这些请求响应结构，SDK 和工具链可以直接复用（注意 base_url 各家不同，路径也可能是 /chat/completions 而不是 /v1/chat/completions）。好处：一套代码多模型切换、便于做降级与比价、迁移成本低。风险：兼容层可能缺失高级能力（如原生结构化输出 schema、思考模式参数），要按厂商文档验证。

<small>标签：生态 · ID：w1-c11</small>

### 12. Python 的 uv/venv 和 Java 的 Maven 怎么对应？

**答**：pyproject.toml ≈ pom.xml（声明依赖与项目元数据）；uv.lock ≈ 依赖锁定（类似 maven 的确定性构建）；venv ≈ 项目本地隔离的运行环境（类似 per-project 的 classpath）；uv run ≈ mvn exec。关键差异：Python 环境隔离是显式的，每个项目一个 venv。

<small>标签：迁移 · ID：w1-c12</small>

### 13. Workflow 和 Agent 的根本区别是什么？

**答**：看控制流由谁决定。Workflow 的路径在运行前就由代码或配置定死，LLM 只在每个节点填内容；Agent 的下一步由模型在运行时决定（说话 / 调工具 / 结束）。判据：选择空间是代码预先给的（例如 routing 只能从预定义的分支里挑），就是 workflow；选择空间由模型当场生成的，才是 agent。

<small>标签：Agent 设计 · ID：w1-c13</small>

### 14. 「固定流程」和「固定代码」是一回事吗？workflow 里的 LLM 知道整个流程吗？

**答**：不是一回事：固定代码是实现细节（函数、if-else），固定流程是业务步骤的顺序，可以写成代码，也可以用 DAG / YAML 配置或低代码画布搭出来；共同点是控制流在运行前已确定。Workflow 里每次 LLM 调用都是独立请求，模型看不到全局流程，也不知道后面还有几步——想让它知道，必须在 prompt 里写清楚它处在第几步。

<small>标签：Agent 设计 · ID：w1-c14</small>

### 15. Anthropic 总结的五种 workflow 模式？各用一句话说明。

**答**：① Prompt chaining 串行拆解：上一步的输出喂给下一步，中间可加校验闸门；② Routing 分流：先分类，再交给专门的流程 / 提示词 / 模型；③ Parallelization 并行：Sectioning 拆成独立子任务，Voting 同一任务多次投票；④ Orchestrator-workers 包工头：主模型当场拆活派给工人再汇总，子任务不预设；⑤ Evaluator-optimizer 写手+编辑：生成与评审循环。共同点：步骤由代码编排，可预测、好测试。

<small>标签：工作流模式 · ID：w1-c15</small>

### 16. Agent 的本质是什么？成立需要哪三个条件？

**答**：本质是 LLM 在循环里根据环境反馈调用工具，不是「更强的模型」。三个条件：① 环境提供真值反馈（工具结果、代码执行、报错）；② 有停止条件（最大步数、预算上限、人工确认点）；③ 能随时把控制权交回人。适合步骤数无法预估、路径无法硬编码的任务。

<small>标签：Agent 本质 · ID：w1-c16</small>

### 17. Agent 里「调哪个工具、走哪一步」是谁决定的？代码还管什么？

**答**：模型决定意图（输出 tool_calls 及参数），代码负责执行与约束。代码仍然决定：工具白名单、工具实现与参数校验、最大步数与预算、哪些动作必须人工确认。一句话：模型决定「做什么」，代码决定「能不能做、能做多久」。

<small>标签：Agent 本质 · ID：w1-c17</small>

### 18. 为什么 Agent 的错误会「累积」？这个数字意味着什么？

**答**：多步串联的成功率是相乘的：每步 95% 正确，10 步全对约 0.95 的 10 次方 ≈ 60%。所以 Agent 必须配沙箱测试、最大步数、失败重试与降级、人工确认点；能用 workflow 解决的，不要用 agent。

<small>标签：可靠性 · ID：w1-c18</small>

### 19. 为什么「工具设计」比 prompt 更值得投入？什么是 poka-yoke？

**答**：工具是模型与外部世界的接口（ACI）。Anthropic 做 SWE-bench agent 时，优化工具的时间超过优化 prompt。做法：描述像给 junior 写 docstring（用途、示例、边界、参数约束），消除格式开销；poka-yoke 防呆——与其提醒模型别用相对路径，不如把参数改成强制绝对路径，让它没有犯错的机会。

<small>标签：工具设计 · ID：w1-c19</small>

### 20. Prompt / RAG / Agent / 微调，按什么顺序上？各自补什么缺口？

**答**：按成本从低到高：Prompt 补指令（角色、格式、约束）；RAG 补知识（私有、时效、可引用，权重不变）；Agent 补行动（工具 + 循环，步骤不确定时）；微调补行为稳定性（风格、格式、降本，最后考虑）。一句话：微调教「怎么说」，RAG 给「说什么」。

<small>标签：选型 · ID：w1-c20</small>
