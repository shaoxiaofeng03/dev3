### 一、先建立模型观：LLM 是下一 token 预测器

调用一次 chat 接口，模型做的事情只有一件：根据你已经给出的全部 token，计算下一个 token 的概率分布，采样一个，追加到序列末尾，再重复，直到遇到停止条件。所谓「生成」，就是一个 token 一个 token 往外蹦。

这个模型观能推出后面所有工程约束：为什么按 token 计费、为什么上下文有上限、为什么同一个问题答案会变、为什么调用之间没有记忆。

### 1.1 一次请求长什么样

OpenAI 兼容协议里，请求的核心是 `messages` 数组。`system` 定角色和规则，`user` 是本次输入，`assistant` 是历史回复（多轮时由客户端回填）。

```json
{
  "model": "deepseek-flash",
  "messages": [
    {"role": "system", "content": "你是严谨的技术助教。"},
    {"role": "user", "content": "用一句话解释 token。"}
  ],
  "temperature": 0.2,
  "max_tokens": 200,
  "stream": false
}
```

响应里最值得看的不是正文，而是三个字段：`choices[0].message.content`（正文）、`choices[0].finish_reason`（为什么停）、`usage`（花了多少 token）。

```json
{
  "choices": [{
    "message": {"role": "assistant", "content": "token 是模型处理文本的最小单位。"},
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 28,
    "completion_tokens": 16,
    "total_tokens": 44
  }
}
```

`finish_reason` 的常见取值：

| 值 | 含义 | 你要做什么 |
| --- | --- | --- |
| `stop` | 正常结束 | 直接使用结果 |
| `length` | 达到 `max_tokens` 被截断 | 输出不完整，考虑调大上限或让模型分段输出 |
| `tool_calls` | 模型请求调用工具 | 执行工具，把结果回填后继续 |
| `content_filter` | 被安全策略拦截 | 换问法或走人工 |

### 1.2 三个必须记住的推论

这三条是后面所有讨论的地基，也是面试里区分「用过 API」和「理解模型」的地方。

::: danger 🔴 面试必背：LLM 的三个工程推论
- 无状态：两次 API 调用之间模型不记得任何东西；多轮对话靠客户端每次把历史消息重发。
- 知识有截止日期：训练数据之后的事情它不知道，除非你放进上下文。
- 输出是采样结果：同一个问题不保证同一个答案；temperature 控制的是随机性，不是「智能程度」。
:::

### 二、token：计价、上下文和延迟的共同单位

token 是模型处理文本的最小单位。它不是字，也不是词，而是分词器（tokenizer）按训练时学到的规则切出来的片段。英文单词可能被切成多个 token，中文一个字也可能对应一个或多个 token，空格和标点同样计入。

### 2.1 怎么估算 token

DeepSeek 官方给出的粗略换算：**1 个英文字符 ≈ 0.3 token，1 个中文字符 ≈ 0.6 token**。据此可以快速心算：

| 输入 | 粗算 token | 说明 |
| --- | --- | --- |
| 1000 个中文字符 | ≈ 600 | 中文文章、聊天 |
| 1000 个英文字符 | ≈ 300 | 英文文档 |
| 1000 行代码 | 往往更多 | 符号、缩进、变量名切得碎 |

这只是估算。不同模型的分词器不同，同一段文本的 token 数可能差很多；真实账单永远以响应里的 `usage` 为准。

### 2.2 usage 与计费公式

```json
"usage": {
  "prompt_tokens": 2000,
  "completion_tokens": 500,
  "total_tokens": 2500,
  "prompt_cache_hit_tokens": 1500,
  "prompt_cache_miss_tokens": 500
}
```

`prompt_tokens` 是输入，`completion_tokens` 是输出。开启思考模式后，reasoning token 也计入输出（以厂商账单为准）。DeepSeek 还会给出缓存命中和未命中的 token 数，因为两者单价不同。

计费公式：`cost = 输入 token / 1,000,000 × 输入单价 + 输出 token / 1,000,000 × 输出单价`。缓存命中的输入 token 按更低的命中价计算。

::: danger 🔴 面试必背：token 与计费
- token 是分词器切出来的最小单位，不是字、不是词；中文与英文的换算比例不同。
- 输入（prompt_tokens）和输出（completion_tokens）分开计价，输出通常更贵。
- 费用 = 输入 token × 输入单价 + 输出 token × 输出单价；缓存命中价通常低一个数量级。
- 永远以响应里的 usage 为准，不要用字数估算做账单。
:::

### 2.3 DeepSeek 价格与时段（2026-11）

下面数字来自官方定价页，单位是「元 / 百万 token」，格式为「空闲 / 高峰」。调价频繁，动手前以官方页面为准。

| 模型 | 上下文 | 最大输出 | 输入（缓存未命中） | 输入（缓存命中） | 输出 |
| --- | --- | --- | --- | --- | --- |
| `deepseek-flash` | 1M | 384K | 1 / 2 元 | 0.02 / 0.04 元 | 4 / 8 元 |
| `deepseek-v4-pro` | 1M | 384K | 4.5 / 9 元 | 0.15 / 0.30 元 | 13.5 / 27 元 |

高峰时段是北京时间周一到周五（不含法定节假日）09:00–12:00、14:00–18:00；其余时间为空闲时段，价格是高峰的一半。批量评测、离线任务放到晚上或周末，成本直接减半。

缓存命中要求前缀完全一致，且由服务端自动判断。把稳定的 system prompt、few-shot 示例、知识库固定头部放在消息最前面，后面的可变内容不影响前缀缓存。

### 2.4 算一笔账

假设 1000 次调用，每次输入 2000 token、输出 500 token，全部缓存未命中，使用 `deepseek-flash` 空闲时段：

```
输入：1000 × 2000 = 2,000,000 token = 2M
      2M × 1 元/M = 2 元
输出：1000 × 500 = 500,000 token = 0.5M
      0.5M × 4 元/M = 2 元
合计：4 元（高峰时段 8 元）
```

如果其中 1500 token 是固定 system prompt 且命中缓存：

```
缓存命中输入：1.5M × 0.02 元/M = 0.03 元
缓存未命中输入：0.5M × 1 元/M = 0.5 元
输出：0.5M × 4 元/M = 2 元
合计：2.53 元，比 4 元省约 37%
```

这就是为什么工程上要「稳定内容放前面、可变内容放后面」：不是为了好看，是直接省钱。

### 2.5 为什么同一个问题费用差很多

::: info 🔵 面试对比：为什么同一个问题，两次调用费用差很多？
- 输出长度不同：最常见，多写 500 token 就是多 500 token 的钱。
- 多轮对话把历史全带上，输入随轮次线性增长。
- 思考模式产生 reasoning token，按输出计费。
- 缓存命中 / 未命中、高峰 / 低谷的单价不同。
- 模型不同、重试次数不同、分词器不同。
:::

### 三、上下文窗口 ≠ 最大输出

这两个概念经常被混为一谈，但它们在预算里扮演不同角色。

### 3.1 两个预算

上下文窗口是本次请求「输入 + 输出」共享的总预算；最大输出是单次生成的上限。以 `deepseek-flash` 为例：窗口 1M，最大输出 384K。你可以输入 900K、输出最多 100K，也可以输入 700K、输出 300K，但两者之和不能超过窗口。

`max_tokens` 只是「最多生成多少」，不是预留。设成 1000 不会提前扣 1000 token 的钱；设得太小，输出会被截断，`finish_reason` 变成 `length`。

::: danger 🔴 面试必背：上下文窗口 ≠ 最大输出
- 上下文窗口 = 本次请求的输入 + 输出共享的总预算。
- max_tokens 只是输出上限，不是预留；设大了不会多收费，设小了会被截断（finish_reason=length）。
- 超窗口必须截断、摘要或检索，不能硬塞。
:::

### 3.2 超窗了怎么办

按代价从低到高：

| 策略 | 做法 | 适用 | 代价 |
| --- | --- | --- | --- |
| 滑窗 | 只保留最近 N 轮 | 闲聊、连续对话 | 丢失早期信息 |
| 摘要 | 把早期对话压成摘要 | 长会话 | 多一次模型调用 |
| 检索 | RAG 只取相关片段 | 知识库问答 | 需要索引和召回质量 |
| 分块 | 把长文档拆成多次调用 | 长文分析 | 需要合并结果 |

不要用「硬塞 + 祈祷」的方式处理超窗：既贵又慢，关键信息还可能被模型忽略。

### 3.3 长上下文的三个代价

第一是钱：输入 token 按量计费，塞满 1M 就是实打实的成本。第二是延迟：prefill 阶段要处理全部输入，上下文越长，首 token 越慢。第三是注意力：模型对长上下文中间部分的信息召回通常弱于开头和结尾（常说的 lost in the middle），所以关键指令和证据要放在显眼位置。

### 3.4 1M 上下文还需要 RAG 吗

::: info 🔵 面试对比：上下文已经 1M，还需要 RAG 吗？
需要，四个理由：
- 成本与延迟：每次塞满都按输入 token 付费，长上下文 prefill 更慢。
- 知识更新：RAG 改索引即可，不用改 prompt、不用重训。
- 权限隔离：检索层可以按用户过滤，塞上下文做不到细粒度授权。
- 可引用：返回片段和来源，才能做溯源和评测。
:::

### 四、采样参数：temperature、top_p、top_k

模型每生成一个 token，都会先得到一个覆盖整个词表的分数（logits），再经过 softmax 变成概率分布，最后从这个分布里采样。采样参数改的就是「怎么从分布里选」。

### 4.1 从 logits 到采样

```
logits z  →  除以 T  →  softmax  →  概率分布 p  →  截断（top_p / top_k）  →  归一化  →  采样
```

temperature 作用在 softmax 之前，改变分布的「尖锐程度」；top_p 和 top_k 作用在 softmax 之后，直接砍掉尾部候选。三者不是同一层的东西，所以同时大改会很难判断效果来自哪里。

### 4.2 temperature

公式是 `p_i = exp(z_i / T) / Σ exp(z_j / T)`。T 越小，大分数和小分数的差距被放大，分布更尖锐；T 越大，分布更平坦，低概率 token 也有机会被选中；T=0 在实际实现中等价于直接取概率最大的 token。

面试里不要只说「temperature 控制创造性」，要说出它改的是概率分布的尖锐程度，以及 T=0 是贪心解码。

::: danger 🔴 面试必背：temperature 与 top_p
- temperature 缩放 logits：p_i ∝ exp(z_i / T)。T 小于 1 更尖锐（更确定），T 大于 1 更平坦（更发散），T=0 等价于取概率最大的 token。
- top_p（核采样）按概率从高到低累加，只保留累计概率达到 p 的最小候选集合，再归一化采样；top_p=1 不截断。
- 两者都在改「从概率分布里怎么选」，不要同时大改；temperature=0 时 top_p 基本不起作用。
:::

### 4.3 top_p 与 top_k

top_p（核采样）先按概率从高到低排序，累加到一个刚好达到 p 的最小集合，只在这个集合里采样。top_p=0.9 表示「只考虑累计概率 90% 的候选」，尾部 10% 直接丢弃。top_k 则是固定保留概率最高的 k 个候选，不管它们的累计概率是多少。

::: info 🔵 面试对比：top_p 和 top_k 有什么区别？
- top_k 固定保留概率最高的 k 个候选，候选数量固定。
- top_p 保留累计概率达到 p 的最小集合，候选数量随分布变化：分布尖锐时少，平坦时多。
- 实践里 top_p 更常用；不少 API 只暴露 temperature 和 top_p。
:::

### 4.4 怎么选值

通用经验：确定性任务（抽取、分类、代码、事实问答）用 0–0.3；通用对话 0.7 左右；创意写作 0.9–1.2。但这只是跨模型的粗略经验，不同厂商对 temperature 的校准不同，不能直接搬数字。

DeepSeek 官方在 2026-11 给出的建议是：代码生成/数学解题 0.0，数据抽取/分析 1.0，通用对话 1.3，翻译 1.3，创意写作/诗歌 1.5。先按厂商建议起步，再用自己的评测集微调。

::: warning 🟠 面试常问：temperature 到底设多少？
- 通用经验：抽取、分类、代码、事实问答用 0–0.3；创意写作用 0.7–1.2。
- DeepSeek 官方建议（2026-11）：代码/数学 0.0，数据抽取/分析 1.0，通用对话 1.3，翻译 1.3，创意写作 1.5。
- 不同厂商的默认值和校准不同，数字不能跨模型直接搬；先按厂商建议，再用自己的评测集调。
:::

::: warning 🟠 面试追问：temperature=0 就每次都一样吗？
不一定。GPU 浮点非确定性、动态批处理、并行归约、模型版本更新都会带来差异；seed 只能降低、不能消除。工程上按「不确定」设计：校验、重试、评测。
:::

### 4.5 其他采样与生成参数

| 参数 | 作用 | 常用值 | 坑 |
| --- | --- | --- | --- |
| `top_p` | 核采样，截断概率尾部 | 0.9–1.0 | 与 temperature 同时大改会互相掩盖效果 |
| `top_k` | 固定保留前 k 个候选 | 视 API 支持 | 不是所有厂商都暴露 |
| `presence_penalty` | 惩罚「已经出现过」的 token，鼓励新话题 | 0–0.5 | 太高会让内容跑题、逻辑断裂 |
| `frequency_penalty` | 按出现次数惩罚，抑制重复 | 0–0.5 | 太高会破坏专有名词和代码 |
| `stop` | 遇到指定字符串停止 | 按业务定 | 命中 stop 时 `finish_reason` 仍是 `stop`，但内容被截断 |
| `seed` | 尽量复现采样 | 固定整数 | 只能降低随机性，不能保证完全一致 |

惩罚项的默认值通常是 0；只有出现明显重复或需要强制换话题时才调。多数业务只调 temperature、max_tokens，必要时加 stop。

### 五、输出控制：max_tokens、结构化输出、思考模式

采样参数决定「怎么选 token」，输出控制决定「生成多少、生成什么形状」。

### 5.1 max_tokens 与 finish_reason

`max_tokens` 是单次生成的硬上限。判断输出是否完整，不要看字数，要看 `finish_reason`：`stop` 才是正常结束，`length` 说明被截断。截断的 JSON 一定解析失败，截断的代码也不可执行。

不同厂商字段名可能不同（例如 `max_completion_tokens`），以对应 API 文档为准；逻辑是一样的。

### 5.2 JSON mode 与校验重试

JSON mode 的服务端约束只保证「输出是合法 JSON」，不保证字段名、类型、枚举值和业务约束。生产流程必须是：拿到文本 → 用 pydantic/JSON Schema 校验 → 失败时把校验错误回填给模型重试 → 仍失败则降级或人工兜底。

DeepSeek 的 JSON 输出还有两个坑：prompt（system 或 user）里必须出现 JSON 字样并给出目标格式样例；`max_tokens` 太小导致截断时，`finish_reason` 可能仍是 `stop`，但 content 会被清洗成空格，看起来像空回复。所以既要给足输出上限，也要对空 content 做兜底重试。

::: warning 🟠 面试常问：JSON mode 能保证字段正确吗？
不能。json_object 只保证「是合法 JSON」，不保证字段名、类型和业务约束。生产做法是 schema 校验 → 把错误信息回填给模型重试 → 仍失败则降级或人工兜底。结构化输出是「校验 + 重试」，不是「让模型别出错」。
:::

### 5.3 工具调用

工具调用（function calling）是把「模型输出结构化意图」做到协议层：请求里带 `tools` 的 schema，模型返回 `tool_calls`（函数名 + 参数），你的代码执行函数，再把结果作为工具消息回填，模型继续生成。

这条链路是 W2 Agent 的基础。今天只要理解两点：模型只负责「决定调哪个工具、传什么参数」，真正执行和权限校验在代码里；工具返回的结果会成为下一轮上下文的一部分，也会计入 token。

### 5.4 思考模式

DeepSeek 的思考模式默认开启。开启后模型会先产生一段 reasoning 内容，再给最终答案；reasoning token 按输出计费，延迟也更高。简单任务（分类、抽取、翻译、格式转换）可以关掉，省钱且更快；复杂推理、数学、多步任务再打开。

```python
extra_body={"thinking": {"type": "disabled"}}
# 需要深度推理时：
extra_body={"thinking": {"type": "enabled"}, "reasoning_effort": "high"}
```

面试里可以把它和成本控制联系起来：同一件事，开着思考可能贵几倍，关掉思考又可能答不对；按任务难度分层，是比「一律用最强模型」更专业的回答。

### 六、延迟与流式

用户感知的「快慢」和账单上的「总时长」不是一回事。把延迟拆开，才知道该优化哪里。

### 6.1 延迟由什么组成

一次调用大致由四段组成：排队与网络、prefill（处理输入，生成首 token）、decode（逐个生成输出 token）、以及客户端处理。常用两个指标：

- TTFT（Time To First Token）：从发请求到收到第一个 token 的时间，主要受输入长度和排队影响。

- 输出速度（tokens/s）：decode 阶段的生成速度，决定长回答的总时长。

近似公式：`总时长 ≈ TTFT + 输出 token 数 / 输出速度`。所以要降低「长回答」的等待，优先减少输出长度；要降低「首屏」等待，优先缩短输入、避免排队。

### 6.2 流式输出

流式用 SSE（Server-Sent Events）把增量 chunk 持续推给客户端，客户端边收边渲染。它不减少总生成时间，但把「等待完整答案」变成「很快看到开头」，感知延迟大幅下降。

实现上要处理：SSE 的半包/粘包、`[DONE]` 结束标记、断流重连、代理层缓冲，以及分别记录 TTFT 和总耗时。结构化输出场景通常不适合流式，因为你必须等完整 JSON 才能校验。

::: tip 🟢 面试加分：流式为什么「感觉快」，但并没有更便宜？
- 首 token 时间（TTFT）远小于完整生成时间，用户先看到内容，感知延迟低。
- 总 token 数和计费完全不变，流式只改变传输方式。
- 工程上要处理 SSE 半包/粘包、断流重连、代理缓冲，并分别记录 TTFT 和总耗时。
:::

### 七、幻觉：来源、缓解与边界

幻觉是模型生成流畅、自信，但事实错误或无法验证的内容。它不是「模型撒谎」，而是下一 token 预测机制在知识不足时仍然继续生成最像答案的文本。

### 7.1 三个来源

| 来源 | 表现 | 对策 |
| --- | --- | --- |
| 知识缺失 | 不知道却编一个 | RAG 提供证据、要求引用原文 |
| 知识过时/训练偏差 | 用旧事实回答新问题 | 检索 + 时效性说明、标注数据日期 |
| 任务超出能力 | 多步推理、精确计算出错 | 拆解任务、给计算器/代码执行工具 |

::: danger 🔴 面试必背：幻觉的三个来源与对策
- 知识缺失 → RAG 提供证据，要求引用原文片段。
- 知识过时或训练偏差 → 检索 + 时效性说明。
- 任务超出能力（多步推理、精确计算）→ 拆解、给工具（计算器/代码执行）、允许说「不知道」。
降低 temperature 只能减少随机性，不能补知识；RAG 能降低但不能消除幻觉，最终要靠评测和人工兜底。
:::

### 7.2 缓解手段与边界

有效的组合通常是：检索到证据 → prompt 要求「只根据给定资料回答，并给出引用」→ 输出结构化答案（答案 + 引用片段）→ 程序校验引用是否存在 → 低置信度时转人工。

注意两个边界：第一，「不要幻觉」这种指令几乎没有约束力；第二，RAG 只能降低幻觉，不能消除，检索错、片段冲突、模型误读都会造成新的错误。

### 7.3 怎么评测

准备一个小型评测集（20–50 条），每条包含问题、标准答案或评分要点。指标至少看三个：正确率、引用命中率（回答里的引用是否真的支持结论）、拒答率（该说「不知道」时有没有说）。每次改 prompt 或换模型都跑一遍，避免「感觉变好了」。

更细的评测可以用 LLM-as-judge，但 judge 本身也会错，关键业务仍要人工抽检。

### 八、参数速查表（今天的交付物）

下面这张表建议自己手抄一遍，或者整理成 `projects/w1/params.md`。面试前只看这张表。

| 参数 | 作用 | 建议 | 常见坑 |
| --- | --- | --- | --- |
| `model` | 选模型 | 简单任务 flash，难任务 pro | 不看任务一律用最贵模型 |
| `messages` | 上下文与角色 | system 放稳定规则，user 放变量 | 多轮忘记回填 assistant 历史 |
| `temperature` | 分布尖锐程度 | 确定性 0–0.3；创意 0.9+ | 与 top_p 同时大改 |
| `top_p` | 核采样截断 | 0.9–1.0 | 以为它能替代 temperature |
| `max_tokens` | 输出上限 | 按业务给足，不设太小 | 被截断后解析失败 |
| `stop` | 停止序列 | 只在不希望出现特定内容时用 | 误伤正文 |
| `presence_penalty` | 鼓励新话题 | 0–0.5 | 太高跑题 |
| `frequency_penalty` | 抑制重复 | 0–0.5 | 太高破坏术语 |
| `seed` | 尽量复现 | 固定整数 | 以为能 100% 一致 |
| `stream` | 流式输出 | 聊天 UI 开，批处理关 | 结构化输出不等完整 JSON |
| `response_format` | JSON 模式 | 配合 schema 校验 | 以为保证字段正确 |
| `thinking` | 思考模式 | 简单任务关，复杂任务开 | 忽略 reasoning token 成本 |
| `timeout` | 客户端超时 | connect 5s，read 60–120s | 不设超时 |

### 8.1 五条使用原则

1. 一次只改一个参数，并且用固定评测集对比；同时改三个参数，你无法判断收益来自哪里。

2. 先定任务类型，再定 temperature；不要从默认值开始盲调。

3. 输出长度是最容易被忽视的成本项：能 200 token 说清的事，不要让它写 1000。

4. 稳定前缀放前面吃缓存，可变内容放后面；这是零成本的优化。

5. 所有调用记录 model、参数、usage、TTFT、总耗时、finish_reason；没有这些数据，优化只能靠猜。

### 九、常见误区速查

| 误区 | 事实 |
| --- | --- |
| token 就是字数 | token 由分词器决定，中文、英文、代码的比例都不同 |
| temperature=0 完全确定 | 浮点、批处理、版本更新都会带来差异 |
| temperature 和 top_p 一起调更好 | 两者作用在同一环节，同时改会互相掩盖 |
| max_tokens 设大更贵 | 它只是上限，不预留、不预付 |
| 流式输出更便宜 | 计费按 token，流式只改传输方式 |
| JSON mode 保证字段正确 | 只保证合法 JSON，业务约束仍要校验 |
| 上下文塞得越满效果越好 | 又贵又慢，关键信息还可能被淹没 |
| RAG 能消除幻觉 | 只能降低，检索和生成都可能出错 |
| 输入和输出同价 | 输出通常更贵，且思考 token 按输出计费 |
| 1M 上下文就不需要 RAG | 成本、延迟、更新、权限、引用都仍然需要 |
