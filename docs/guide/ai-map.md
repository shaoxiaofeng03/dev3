# AI 应用技术地图

![AI 应用技术地图](/ai-map.svg)

<small>手机上字小的话，[点这里打开原图](/ai-map.svg)，可以直接双指放大。</small>

这是一张**分层地图**，不是知识清单：它回答的是「一个 AI 应用从用户看到的产品，到跑在底下的基础设施，中间要经过哪几层、每层解决什么问题」。

（图是 SVG，可直接放大看；源文件在 `scripts/build-ai-map.mjs`，改完跑 `node scripts/build-ai-map.mjs` 重新生成。）

## 一、六层分别解决什么

| 层 | 解决什么问题 | 代表技术 | 对应周次 |
| --- | --- | --- | --- |
| **应用层** | 给谁用、什么形态 | 智能客服、企业知识库、代码助手、文档抽取、数据分析、流程自动化 | 贯穿全程，W7 / W13 做产品化 |
| **编排层** | 谁决定下一步：代码还是模型 | Prompt 链、路由、并行投票、包工头模式、生成-评审、ReAct、计划-执行、多智能体 | W2 手写循环，W8–W10 范式 |
| **能力层** | 让模型会查、会做、靠谱 | 检索 RAG、工具调用、记忆、结构化输出、评测、可观测、护栏、缓存成本 | W3–W7（RAG）、W9（记忆）、W10（评测） |
| **模型层** | 选哪个模型、要不要改它 | 对话模型、推理模型、长上下文、Embedding、Rerank、多模态、小模型、微调 | W1 选型，W3 向量，W14 Java 接入 |
| **基础设施层** | 跑得稳、跑得省 | 推理服务、向量库、模型网关、队列缓存、监控告警、GPU | W4 部署、W6 生产化 |
| **横切关注点** | 每一层都要管的事 | 评测数据飞轮、成本与延迟、安全合规、权限审计 | W4 起每周都要碰 |

## 二、怎么读这张图（三步）

**第一步：认层。**
从上往下问自己三个问题：这个产品给谁用？它的步骤是代码定还是模型定？它靠什么保证不出错？——分别对应应用层、编排层、能力层。

**第二步：看层间流动。**
- 用户的问题从**应用层**进入
- 由**编排层**决定走哪条路径
- 需要外部知识/动作时调**能力层**
- 能力层最终落到**模型层**（生成、embedding、rerank）
- 全部跑在**基础设施层**上
- 横切关注点像“电网”，每一层都要接

**第三步：标位置。**
在图上标出你**现在会什么**、**三个月后要会什么**。这是你的学习进度条，不是别人的。

## 三、这张图想纠正的三个误区

**① 只盯模型层。**
“哪个模型最强”是最容易讨论、也最容易过时的问题。真正决定产品能不能用的是**能力层**（检索准不准、评测算不算得清）和**编排层**（控制流稳不稳）。

**② 把 RAG 当成模型能力。**
RAG 在**能力层**，不在模型层。模型权重没变，只是上下文里多了检索结果。所以“换个更强的模型”救不了烂检索。

**③ 忽略横切。**
成本、延迟、权限、审计不是“上线后再补”的，它们决定架构：权限过滤要下推到检索层，缓存策略要跟知识更新绑定，评测集要跟需求一起长。

## 四、和你 20 周计划的对应

```
W1–W4   模型层 + 能力层的地基（API、结构化输出、工具调用、最小 RAG）
W5–W7   能力层做深（混合检索、rerank、评测、权限、成本）
W8–W13  编排层做深（ReAct → 计划执行 → 多智能体 → 评测与可观测）
W14–W15 把能力接进 Java 服务（模型网关、多模型路由、审计）
W16–W20 把这张图讲成面试答案
```

面试时如果被问“你理解 AI 应用开发吗”，**不要从模型讲起，从这张图讲起**：应用 → 编排 → 能力 → 模型 → 基建 → 横切。三层之后，面试官就知道你不是只会调 API 的人。
