# /week-review · 证据驱动的周复盘

只根据证据下结论；数据缺失就说缺失，不要编完成度。

## 步骤

1. 确定周次与日期范围：
   - 参数 `w1` / `1` 直接使用；没有参数则用今天所在周。
   - 从 `docs/data/plan.json` 读 `start`、`end`、`days`。
2. 收集证据：
   - `docs/data/checkins.json`：本周每天的 `items`、`note`、`logs`、`minutes`。
   - `git log --since=<start> --until=<end+1天> --oneline` 与 `git diff --stat`（本周相关提交）。
   - `projects/` 下本周新增/修改的文件；有测试就看测试。
   - 若用户提供 `/quiz` 成绩，一并纳入。
3. 读 `docs/plan/week-NN.md` 的交付与验收、`docs/study/wNNd*.md` 的自检问题。
4. 输出：
   - **计划 vs 实际**：按天列完成/未完成；未完成标注可能原因（估时/打断/概念卡住）。
   - **交付物证据**：每项交付物对应 commit/file/test；区分「能跑」和「已验证」。
   - **卡点聚类**：把 logs 里的 blocker 归成 2–3 类，给根因，不要只复述。
   - **面试准备度**：本周 3 个最稳的概念、3 个最虚的概念。
   - **下周只改一件事**：一个具体动作（例如「每天先写 5 行再读讲义」），不要列五条。
   - **复盘草稿**（严格用站点格式）：
     ① 最大卡点：...
     ② 下周只改一件事：...
     ③ 本周最值钱认知：...
5. 默认只输出草稿，不写入 `docs/data/checkins.json`；用户明确要求「保存」时再写入周日的 `retro` 字段，并提醒提交。

## 规则

- 每条结论带证据：日期、commit、文件或打卡记录。
- 不把「看了讲义」算作交付；交付必须有可运行/可验证的产物。
- 不因为打卡全勾就判定达标；看交付物和测试。
